# FeedLizard Linux distribution

FeedLizard Linux uses GitHub for source, CI, prerelease artifacts, and release
coordination. Every public release below 1.0 is beta software. Version 1.0 is
the first stable release.

## Version and release gate

The application version is the workspace package version in the root
`Cargo.toml`. The graphical application inherits it, About formats a SemVer
`-beta.N` suffix as `Beta N`, AppStream carries the same machine version, tags
are `vVERSION`, and release filenames derive from that tag. The
`scripts/release-version.sh` gate rejects a mismatched tag or AppStream entry.

Normal pushes and pull requests run formatting, tests, Clippy, release builds,
dependency policy, and Flatpak manifest validation. Only a deliberate tag that
matches `v0.*-beta.*` invokes the beta release workflow. GitHub Releases created
by that workflow are prereleases and contain architecture-specific bundles plus
`SHA256SUMS` generated from those exact bundles.

## Application identity and channel

All releases use application ID `io.github.feedlizard.FeedLizard` and Flatpak
branch `release`. Beta status lives in the SemVer/AppStream/GitHub release
metadata rather than a second application ID or sandbox. The same ID and branch
continue at 1.0, so Flatpak updates preserve the SQLite database, settings,
cache, and Secret Service association. There is no FeedLizard self-updater.

## Standalone bundle

Install a downloaded bundle with:

```sh
flatpak install --user ./FeedLizard-VERSION-ARCH.flatpak
```

Flatpak can fetch the declared GNOME runtime if it is missing, so this is not a
promise of a fully offline install. Verify the asset first with `sha256sum -c
SHA256SUMS` from the directory containing all named release artifacts.

## Updateable repository

The repository is an ordinary signed Flatpak/OSTree archive, not a proprietary
update service. `FeedLizard.flatpakref`, generated with
`scripts/make-flatpakref.sh`, contains the repository URL, `release` branch,
runtime repository, and base64 production public key. Users then install with:

```sh
flatpak install --user FeedLizard.flatpakref
flatpak update io.github.feedlizard.FeedLizard
```

A local disposable-key repository is used for architecture and update tests.
Production publication remains disabled until a long-lived signing key is
explicitly authorized.

GitHub Pages can serve the static repository over HTTPS, but its documented
deployed-site size limit makes it appropriate only while the repository remains
small. Publication must enforce a conservative size gate and retain GitHub
Release bundles as the durable fallback. The repository URL is metadata-only,
so a later move to a custom domain or object/static hosting does not require an
application change. Do not couple update behavior to GitHub Pages.

## Production signing model

Use a dedicated offline-generated OpenPGP signing key solely for FeedLizard's
Flatpak repository. The public key is embedded in the `.flatpakref` and offered
with repository installation. The private key must never enter source, release
assets, logs, pull requests, or developer databases. CI should import it only
inside a protected release environment from an encrypted Actions secret, use
least-privilege release permissions, and destroy its temporary keyring when the
job ends.

Keep two encrypted offline backups of the private key in separate controlled
locations plus a recorded revocation certificate and key fingerprint. Losing
the key prevents trustworthy updates for existing repository users; compromise
requires publishing a signed transition where possible, rotating the public
key, and clearly instructing users to re-add the repository. Rotation should be
planned before expiry, with an overlap release signed according to Flatpak's
supported trust-transition procedure.

Required protected-environment secrets are conceptually:

- `FLATPAK_GPG_PRIVATE_KEY`: armored private signing key;
- `FLATPAK_GPG_KEY_ID`: exact signing fingerprint;
- `FLATPAK_GPG_PUBLIC_KEY`: armored public key for `FeedLizard.flatpakref`.

No production key is generated by repository tooling.

## Repository retention and rollback

Flatpak/OSTree provides normal deployment rollback (`flatpak update --commit=…`
when the commit is still present). FeedLizard does not add a rollback system and
does not promise indefinite retention. Repository maintenance should preserve
the current release and a deliberately chosen rollback window for both
architectures, verify clients can update from the oldest retained deployment,
then run `flatpak build-update-repo --prune` only as a reviewed release operation.
Monitor repository size before each publication; never delete objects blindly.

## Architecture truthfulness

CI uses native GitHub-hosted x86-64 and aarch64 runners for build and test jobs.
Fedora aarch64 is the current native graphical runtime-validation environment.
Successful CI is build/test validation, not a claim of real x86-64 desktop or
multi-distribution runtime testing.
